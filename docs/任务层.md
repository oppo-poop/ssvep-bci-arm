# 任务层：场景、原语与取放序列

> 建立于 2026-10-17，2026-10-18 补任务逻辑。包位置 `star-arm-moveit2/src/roarm_task`。
> 上游是 `scripts/roarm_cli.py`（已验证的终端控臂），下游仍是同一套 MoveIt 接口。

## 一、结构

```
ros2 run roarm_task task          ← 入口
        │
   scene.py                       ← 这一次抓什么、放哪里
        │
   sequence.py                    ← 十个阶段 + 失败归因 + 抓取重试
        │
   primitives.py                  ← 七个动作 + 抓取校验，只管算坐标
        │
   link.py                        ← 子进程调用 roarm_cli.py
        │
   roarm_cli.py                   ← 发话题 + TF 到位校验 + 三档退出码
        │
   arm_moveit_write → move_group → fake 控制器 / 真机
```

**为什么任务层要绕一层子进程，而不是自己发 ROS 消息？**

因为「到位了没有」只能有一个判据。CLI 里已经有 TF 实测 + 连续三次进容差 + 三档退出码；
任务层再自己判一次，就会出现两套判据，迟早漂移。代价是每个原语多 0.5~1 s
（一次取放 10 步约多 7 s，总时长 38 s 左右）。

## 二、场景（`scene.py`）

一次取放的全部输入收成一个不可变对象：

| 字段 | 含义 | 默认 |
|---|---|---|
| `pick` / `place` | 末端取物点 / 放置点（世界系，米） | 见 `Scene.default()` |
| `object_height` | 物体高度，决定抬起量 | 0.05 m |
| `object_width` | 物体宽度，抓取校验时判断夹爪该停多开 | 0.03 m |
| `standoff` | 接近/撤离时高出目标多少 | 0.08 m |
| `clearance` | 抬起后离台面的净空 | 0.06 m |
| `verify_grasp` | 是否校验「真的夹住了」 | false |

派生量：`lift_height = object_height + clearance`，接近点/撤离点 = 目标点 + `standoff`。

**为什么要单独抽这一层**：视觉、眼动、终端手动输入，最终产出的都是「一个取物点 + 一个放置点」。
把共同形状固定成 `Scene`，将来换输入源时任务层一行都不用改。

**边界校验不在这里做**。工作区越界由 `roarm_cli` 负责（它才是发指令的那一层），
`scene.problems()` 只查逻辑合理性：高度为正、取放点不重合、抬起量大于接近偏移。同一个判断不做两份。

载入方式：

```bash
ros2 run roarm_task task --scene demo        # 包内简写，读 share/roarm_task/scenes/demo.yaml
ros2 run roarm_task task --scene ./my.yaml   # 任意路径
ros2 run roarm_task task --pick 0.33 -0.30 0.10 --place 0.45 0.05 0.25
```

## 三、十个阶段

| # | 阶段 | 动作 |
|---|---|---|
| 1 | 准备 | 回笛卡尔 home |
| 2 | 接近 | 移到取物点正上方 |
| 3 | 下探 | 竖直到取物点 |
| 4 | 合爪 | 合拢 + 可选校验 + 夹空重试 |
| 5 | 抬起 | 竖直到 `pick.z + lift_height` |
| 6 | 递送 | 平移到放置点上方（保持夹持） |
| 7 | 放置 | 竖直到放置点 |
| 8 | 释放 | 两指张开 |
| 9 | 撤离 | 竖直到放置点上方 |
| 10 | 完成 | 回 home |

阶段标记不只是给日志看的：**失败时要靠它判断该不该重试**。合爪失败可以重来，
越界失败重来一万次也一样，所以只有第 4 步有重试逻辑。

## 四、夹爪口径怎么隔离的

2026-10-17 实测（TF 量两指间距）：

| CLI 命令 | 舵机角 | `joint7_left` | 两指间距 |
|---|---|---|---|
| `open` | 100° | 0.000 m | **0 mm（合拢）** |
| `close` | 0° | −0.025 m | **50 mm（张开）** |

命令名与物理效果相反。当天决定走**方案 C**：不猜，等实机量一次再定名。

所以任务层**不写 `open`/`close` 字面量**，只用物理语义：

```python
# config.py
GRIP_CMD = {
    "close_fingers": "open",    # 合拢 = 物理夹住
    "open_fingers":  "close",   # 张开 = 物理松开
}
```

实机标定后方向一致就一行不改；相反只改右边两个字符串，任务逻辑不动。

另一个未定项：`close` 的 0° 对应 −0.032 m，超 URDF 下限 −0.025 约 28%，
仿真桥会夹紧并打 WARN。改 URDF 限位还是收窄角度，同样等实机量。

## 五、抓取校验（重要，别误读）

合爪后读 `joint7_left`，换算两指间距（`gap_mm = -joint7_left × 2000`）：

| 间距 | 判定 |
|---|---|
| < 2 mm | 夹空（两指合到底） |
| ≤ 物宽 + 3 mm | 夹住 |
| 更大 | 没夹到（物体不在指间） |
| 读不到 | 不阻断，但在结果里注明 |

判夹空时会走一次完整重试：`张开 → 退回接近点 → 重新下探 → 再合`，最多 `GRASP_MAX_RETRY` 次，
仍失败则中止序列并自动回位。

⚠ **仿真里这个判据必然判「夹空」。** FakeSystem 不模拟接触，夹爪设多少就是多少，
所以合爪后 `joint7_left` 恒为 0。因此 `verify_grasp` 默认为 false，
`--verify-grasp` 只是给你**验证这条逻辑本身**用的：

```
4  合爪夹持  FAIL  15.6s  连续 2 次未夹住（间距 0.0 mm，合到底 → 判夹空），放弃该目标
在「合爪夹持」（合爪阶段）失败，3/4 步通过
（已自动回位）
```

这条失败输出是**正确行为**，证明校验没有流于形式。要真正判「抓住没有」，
必须上真机或改用 Gazebo 物理仿真。

## 六、用法

```bash
source /opt/ros/humble/setup.bash
source star-arm-moveit2/install/setup.bash
bash scripts/sim_up.sh                     # 起仿真（含夹爪桥）

ros2 run roarm_task task --dry-run         # 只列场景与步骤
ros2 run roarm_task task                   # 跑一次完整取放
ros2 run roarm_task task --scene demo
ros2 run roarm_task task --verify-grasp    # 仿真里预期失败（见第五节）
```

退出码：`0` 全通过 / `1` 某步失败（会指出哪一步、哪个阶段）/ `2` 场景自检不通过（一条指令都不发）。

失败处理：任一步失败立即停，并按配置尝试回位。回位本身失败会额外提示「臂可能停在半空」，
但不掩盖原始失败。

## 七、已知限制

- **仿真里没有物体。** 序列跑通只证明「臂按计划到了位置、夹爪按计划开合了」，
  **不证明真的抓起了东西**。`pick` / `place` 默认值也是 README 路点的占位，不是标定值。
- **抓取成功无客观判据（仿真）**，理由见第五节。
- **无碰撞规划**：`sensors_3d` 已置空，场景里没有障碍物。
- **`home` 不是关节零位**，是笛卡尔点，IK 会解出 j4≈5.9° / j6≈−5.9°。
- **速度来自 yaml 的 `default_velocity_scaling_factor`（0.1）**，真机上仍需复核。
