## 一、这是什么

脑控机械臂。SSVEP 意图解码沿用 `../ssvep-bci`（脑控小车），**执行端换成 Starai Cello 从臂**，
走 ROS 2 / MoveIt2 / Gazebo。2026-09-15 与小车项目正式解耦。

两个项目的分工是清楚的：`ssvep-bci` 负责"意图从哪来"（采集→CCA→dwell→阈值→`k`），
`ssvep-Roarm` 负责"意图变成什么动作"（`k` → 任务原语 → MoveIt 规划 → 舵机总线）。

## 四、cello / viola 判别：实算复核（**结论：README 的技术描述有错**）

`src/` 下同时有 cello（从臂）和 viola（主臂）两套完整模型，**关节名、关节限位、夹爪类型全同，
只有连杆长度不同** —— 拿错了不报任何错。唯一判别办法是实算臂展。

本次用 URDF 关节原点 + 轴向量独立重算了 FK 与随机采样最大臂展：

| | `cello_description` ✅ 用这份 | `viola_description` |
|---|---|---|
| **到腕法兰最大水平臂展** | **686.4 mm** | **469.7 mm** |
| 含夹爪指尖臂展 | 708.8 mm | 499.4 mm |
| 零位末端（腕法兰） | **(0.4796, 0, 0.3568)** | (0.3502, 0, 0.2296) |
| 零位末端（含指尖） | (0.4933, 0, 0.3568) | (0.3603, 0, 0.2296) |
| 规格表对应 | 650 / 全展 1340（÷2=670） | 470 / 940 |

- **cello 686.4mm 与规格 650mm（含末端法兰）对得上；viola 469.7mm 与 470mm 吻合。判别有效。**
- cello 零位腕法兰 `(0.4796, 0, 0.3568)` 与工程 README 记录的 `Cello Home (0.479, 0, 0.369)` 吻合，
  4 个记录路点全部落在可达空间内（最远 `Cello right` 3D 半径 0.594 m < 0.686 m）。
- 关节限位实测：cello `±2.27 / ±1.57 / ±1.57 / ±2.27 / ±1.57 / ±2.27` —— 与 README 一致。

### ❌ README 的一处错误

项目 README §三 的对照表写"夹爪 prismatic −0.025 m · **完全相同**"。实测不成立：

| 模型 | `joint7_left` | `joint7_right` | mimic |
|---|---|---|---|
| `cello_description.urdf` | −0.025 ~ 0 ✅ | −0.025 ~ 0 ✅ | ✅ |
| `viola_description.urdf` | −0.03 ~ 0 | **−3.14 ~ 3.14** ⚠ | ✅ |
| `cello_gazebo.urdf` | −0.03 ~ 0 | **−3.14 ~ 3.14** ⚠ | ✅（Gazebo 不支持） |
| `viola_gazebo.urdf` | −0.03 ~ 0 | **−3.14 ~ 3.14** ⚠ | ✅（Gazebo 不支持） |

**四个模型里只有 `cello_description.urdf` 的夹爪限位是干净的。** 这不是学术细节，见 §六·J。

### 速率账（实测，纠正一处说法）

- `ros2_controllers.yaml`：`controller_manager.update_rate = 100 Hz`
- `robo_driver`：`create_timer(0.03, ...)` → **joint_states 反馈率 33.3 Hz**
- 舵机总线：`SERVO_BAUDRATE = 1_000_000`

项目 README §七 写的"舵机总线 @200Hz"在代码里找不到依据。**实际链路是 100 Hz 控制器 / 33 Hz 反馈**，
反馈比控制器低 3 倍 —— MoveIt 拿到的是 30ms 前的位姿。这个数字应该按实测写。

## 六、代码级问题清单（按严重度）

### P0 — 装真机前必须改

**A. joint6 速度限值三级叠加，最终可达 753°/s**
1. `joint_limits.yaml` 写 `joint6.max_velocity: 13.14`，其余关节 3.14（**4.18× 同级**，且 cello / viola 两份都有，是系统性复制开的）
2. URDF 声明 `velocity="1"`（57°/s），yaml 写 3.14（180°/s）→ **3.14×**
3. `joint_limits.yaml` 的 `default_velocity_scaling_factor: 0.1` 被 `arm_moveit_write.cpp` 的 `setMaxVelocityScalingFactor(1.0)` 顶掉 → **再 10×**

三级叠加后，规划器可以让腕部以 **13.14 rad/s ≈ 753°/s** 甩动。臂在人旁边时这是实打实的伤人风险。
**必须两处 yaml 同改**，建议关节统一到 ≤1.57，joint6 单独设更低。

**B. 上电即无条件回零，且中途有 100ms 掉力矩**
`robo_driver.__init__` 调用 `uservo_ex.__init__` → 先 `reset_multi_turn_angle(0xff)`
（内部含 `disable_torque`）→ `time.sleep(0.1)` → 若 `lock=enable` 立即 `arm_move_by_time()`
把 7 个关节全部驱到 `ZERO_ANGLE`（夹爪 50°），`interval=1500(+400)=1900ms`。

**后果**：臂若不在零位，上电瞬间会自己甩过去；期间有 100ms 完全没有保持力矩，悬空臂会掉。
项目 README 写"上电必须回零/自检通过才接受命令"，但代码现在是**无条件**执行，没有自检、没有当前位姿判断。
脑控场景（人就在旁边）必须改成"先读回当前角度 → 软启动 → 限幅趋近"。

**C. 取消无效 —— 急停不可依赖软件**
`cello_controller.arm_cancel_callback()` 返回 `CancelResponse.ACCEPT`，
但 `arm_execute_callback()` 的 `for pt in trajectory.points` 循环**从不检查 `goal_handle.is_cancel_requested`**。
取消请求会被接受然后被完全忽略，轨迹照跑到底。

→ 上层（MoveIt / 未来 SSVEP 层）以为能停，实际停不下来。
**硬件急停（切舵机动力）必须独立于 PC 与 ROS 2 实现，这是唯一可靠的停止手段。**

### P1 — 会静默出错，不报错误

**D. 轨迹时间账每点错 400ms**
`cello_controller` 发 `time=[int(duration*1000)]`（轨迹点间隔），然后 `time.sleep(duration)` 就发下一点。
但 `robo_driver.set_angle_callback` 做 `interval = int(msg.time[i]) + 400`，`acc = dec = interval/2`。

→ 舵机实际执行时间是 `duration + 400ms`，控制器却只等 `duration`。
**N 个轨迹点累积超前 N×0.4s**，中间点永远追不上，实际轨迹比规划的时间轴拉长。
这个 +400 是硬编码的固定补偿，两边的常量没有对齐。

**E. ~~4 个 launch 文件名构建错了~~ → ❌ 本条是误判，已撤销（2026-10-07 实测）**

原判断：`MoveItConfigsBuilder("cello")` 会去找 `cello.urdf.xacro` 而实际叫 `cello_description.urdf.xacro`，故 4 个 launch 跑不起来。

**实测推翻**：`moveit_configs_builder.py:160` 是

```python
super().__init__(package_name or (robot_name + "_moveit_config"))
```

`MoveItConfigsBuilder("cello")` → `package_name` 为 None → **自动拼成 `cello_moveit_config`**，包名解析完全正确。
再往下，`config/cello.urdf.xacro` 确实不存在（第 171 行 `.exists()` 为假），但它会**回退到 `.setup_assistant`** —— 该文件里记着

```yaml
urdf:
  package: cello_description
  relative_path: urdf/cello_description.urdf
```

于是加载 `cello_description/urdf/cello_description.urdf`。**能跑。**

实测对比两种写法的产物：

| 写法 | URDF 长度 | 差异 |
|---|---|---|
| `MoveItConfigsBuilder("cello")` | 9384 字符 | 走 `.setup_assistant` 回退 |
| `MoveItConfigsBuilder("cello_description", package_name="cello_moveit_config")` | 10647 字符 | 走 `config/*.urdf.xacro` |

两份 URDF **除一段 `<ros2_control name="FakeSystem">`（mock 硬件插件）外逐字节相同** —— 同连杆、同关节限位、同 mesh。
而这段 ros2_control 只被 `ros2_control_node` 消费（由 `demo.launch.py` / `driver.launch.py` 另行加载），
`arm_moveit_write` 只用 `robot_description` 做 IK 与碰撞检查 → **对它无影响**。

**结论：4 个 launch 都能用，无需修改。** 统一成 `("cello_description", package_name="cello_moveit_config")` 只是风格一致，
不是修复。**（"`topic_publisher.cpp` 已有模板"这句仍然成立。）**

**F. 夹爪三条控制路径、三套角度口径，互不一致**

| 路径 | 代码位置 | "开" | "合" |
|---|---|---|---|
| 手动 topic（绕过 MoveIt） | `arm_moveit_write.cpp::control_gripper` | `100.0` 度 | **`0.0` 度** |
| MoveIt 动作 → 控制器 | `cello_controller.gripper_execute_callback` | 米制转角度：`m/0.032*100+100` | URDF 限位 [−0.025, 0] → **100° ~ 21.875°** |
| 启动回零 | `robo_driver.ZERO_ANGLE[6]` | — | `500`（0.1°单位 = **50°**，即"半开"） |
| LeRobot 真机驱动 | `starai_cello.move_to_initial_position` | — | `gripper=50`（RANGE_0_100 归一化） |

**核心矛盾**：URDF 限位 −0.025 m 换算成舵机角度下限是 **21.875°**，而 `arm_moveit_write` 的 "close" 命令是 **0.0°**
→ 对应 −0.032 m，**超出 URDF 限位 28%**。

→ 仿真里验过的夹爪行程 ≠ 手动路径实际执行的。阶段 1 之前必须先钉死一张"开/合 ↔ 舵机角度"对照表。

**G. `hand` 规划组里没有关节**
SRDF `<group name="hand">` 只列了 `<link name="link7_left"/>` / `<link name="link7_right"/>`，**没有列 joint**。
配合 `moveit_controllers.yaml` 里 `hand_controller: default: true`
→ MoveIt 默认把夹爪指令发给一个规划不动的组。实际能动的只有 §六·F 那条绕过 MoveIt 的 topic 路径。
（另注：SRDF 的 `<group name="arm">` 里列了 `<joint name="virtual_joint"/>`，一个 fixed joint，MoveIt 会报无用配置。）

**H. 加速度约束形同不存在**
全部 7 个关节 `has_acceleration_limits: false` / `max_acceleration: 0`。
上层 `setMaxAccelerationScalingFactor(0.5)` 是"缩放一个不存在的上限"，没有约束效果。
规划出的是梯形速度曲线，起停都是阶跃加加速度 —— 脑控场景应打开并设上限。

**I. 串口硬编码**
`robo_driver.py`：`SERVO_PORT_NAME = "/dev/ttyUSB0"` 写死，节点未 `declare_parameter`。
换口必须改源码或做 udev 规则。另外 `SetAngle.msg` 定义了 4 个字段
（`servo_id` / `target_angle` / `time` / `speed`），`robo_driver` **从不读 `speed`**，真正生效的是 `time`。

### P2 — 模型/仿真一致性问题

**J. Gazebo 不支持 `<mimic>`，而 gazebo 模型里右指限位是 ±3.14 m**
`joint7_right` 在 URDF 里是 `<mimic joint="joint7_left"/>` 的从动指。
但 Gazebo 的 URDF→SDF 转换**不支持 `<mimic>`**，而 `cello_gazebo.urdf` / `viola_gazebo.urdf` 里
`joint7_right` 的限位写成了 **−3.14 ~ 3.14**（正确值应为 −0.03 ~ 0）。

→ 一旦启用 Gazebo 物理仿真，右指会跑飞 **3 米**。
（这也反向支持了项目 README §八 的判断："先不要上 Gazebo"。但若将来要上，这处必须先修。）

**K. `joint7_left` 限位在 description 与 gazebo 之间也不一致**
`cello_description.urdf` 是 −0.025，`cello_gazebo.urdf` 是 −0.03。同一条臂的两份模型对不上。

**L. `robo_driver.set_angle_callback` 冗余写总线**
`for i in range(len(msg.servo_id))` 循环体内调用 `self.arm_move_by_time()`，
而 `arm_move_by_time()` 内部是**全 7 轴 sync 写**。一条 7 轴命令 → 触发 7 次全轴同步写。

### 唯一的概念接口（在 `ssvep-bci` 侧）

**`drive_pilot.py` 是现成可复用的模板** —— 它已经是"纯逻辑状态机 + 无硬件依赖"的形状，

## 十、当日实录：MoveIt 装上、构建跑通、阶段 0 完成

### 10.1 安装 MoveIt：上游 README 的写法两个方向都不对

| 写法 | 结果 |
|---|---|
| `apt install ros-humble-moveit*`（上游文档） | ❌ 拉进 33 个 `-dbgsym`（659 MB，其中 528 MB 是调试符号）；且**包含与 `moveit-py` 冲突的 task-constructor，unpack 直接失败** |
| `apt install ros-humble-moveit`（metapackage） | ❌ 38 包 / 10 MB，但**不依赖** `joint_trajectory_controller` / `gripper_controllers`，而 `ros2_controllers.yaml` 正需要这两类 |
| **同范围 + 排 dbgsym + 排 task-constructor + 显式补两个控制器** | ✅ 46 个包 / 131 MB |

**task-constructor 冲突的本质**（ROS 2 Humble 上游 Debian 打包 bug）：
`ros-humble-moveit-py` 与 `ros-humble-moveit-task-constructor-core` 都声称拥有
`/opt/ros/humble/local/lib/python3.10/dist-packages/moveit/__init__.py`，
两者都没声明 `Replaces`/`Breaks`，dpkg 拒绝覆盖。
实测两边文件交集**只有这 1 个**（81 vs 127 个文件）。

⚠ **不要用 `dpkg -i --force-overwrite`**：

| 包 | `moveit/__init__.py` |
|---|---|
| `moveit-py` | `from moveit.core import *` / `from moveit.planning import *` |
| `task-constructor-core` | `__path__ = pkgutil.extend_path(__path__, __name__)` |

覆盖后 `import moveit` 会**静默失去** `core`/`planning`（不报错，等用 Python 调 MoveIt 才 AttributeError）。
而反向依赖显示除 TMC 自家包外无人依赖它，项目源码 **0 处**引用 → 直接摘掉是零代价的。

脚本：`scripts/install_moveit.sh`（干净安装）、`scripts/fix_moveit_install.sh`（半装状态修复）。

### 教训

**同名包分布在多个工作区时，`ros2 pkg prefix <name>` 是唯一的真相检查**，光看"能不能跑起来"看不出来。
本项目的这类静默错误已出现三次：cello/viola 模型混淆（§三）、路径挂载（§十）、工作区同名包（本节）——
共同点都是**不报错，但跑的不是你以为的那份**。**进入真机阶段前，每次开工先核一次 `ros2 pkg prefix`。**
